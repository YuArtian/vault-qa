# 检索翻车案例

日常使用中记录关键词检索挑错笔记的案例。**这份账本就是 v3（向量检索）的验收测试集**：换新检索后拿同样的问题重跑，逐条对比是否还翻车。

## 记录格式

一行一案：提问原文、应该挑中什么、混进来什么噪音、翻车原因。判定标准不追求完美——「明显不该出现的笔记出现了」就算翻车。

| # | 日期 | 问题 | 应该挑中 | 混进来的噪音 | 肇事原因 |
|---|------|------|---------|-------------|---------|
| 1 | 2026-07-24 | js的装饰器是什么？ | 2.01 装饰器与闭包 | npm i & npm ci、报错、consola、lock 文件 | `js` 作为子串命中 json / Next.js / .js，JS 目录笔记集体白得分 |
| 2 | 2026-07-31 | py中有哪些类型 | 1.01 数据类型基础 | 5.05 argparse 命令行参数、localhost 和 127.0.0.1 的区别 | `py` 作为子串命中 python / .py / mypy，几乎每篇技术笔记都含 |

## 已知的病根（v3 前的临时修补方向）

- **短英文词的子串匹配**：`text.count(w)` 不认单词边界——待做练习：ASCII 词改 `re.findall(r"\b词\b", text, re.IGNORECASE)`（能修 #1、#2）
- **两字滑窗的语义盲区**：「是什」「什么」这类窗口毫无区分度，靠 IDF 压制但治标——关键词方案的天花板，根治靠语义检索（v3）

## v3 验收方式

```text
对每个案例：用新检索重跑问题 → 记录挑中列表 → 和本表对比
通过标准：应该挑中的仍在前排，噪音列的笔记消失
```

同场加试（关键词方案的死穴题）：

- 「怎么让程序同时干几件事」→ 向量首位命中《4.03 并发编程》（字面零重叠）；关键词方案首位是无关的《Vector Database》
- 回归题（conda 磁盘、os.environ）→ 向量首位均正确，未顾此失彼

**新观察：向量有自己的「软噪音」**——语义近邻但实际无关的笔记会混进候选（问 js 装饰器带出《React 渲染机制》，问 conda 磁盘带出《collections 高级容器》）。天花板换了形状：关键词输在「字面同、语义异」，向量弱在「语义近、主题偏」+ 专有名词/编号不精确。两者互补 → 混合检索（关键词 + 向量 + RRF 融合）是后续方向。
